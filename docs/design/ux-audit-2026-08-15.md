# UX & functionality audit — the phone

- **Audited:** 2026-08-14 → 2026-08-15
- **Auditor:** Claude Opus 5 (session `agent/ux-audit`)
- **Target:** `origin/main` @ `23e8581`
- **Scope:** the product as a person meets it. Not the codebase, not the tests.
- **Status:** findings only. **Nothing was fixed.** The fix plan is §6.

---

## 1. Verdict

**No. Siyur is not usable on a phone today, and the primary reason is not polish — it is that
the first step of the product cannot be completed with a thumb.**

At 390 × 844 (iPhone 14), the control that delimits an area from the map — `Use this view`,
which resolves in **0.18 s** — is painted underneath the "Plan a day" panel and is
unreachable in every scroll state. The only delimit control a thumb *can* reach is the search
pill, and that path takes **61.6 seconds** to return a `404` carrying 20 disambiguation
candidates, which the client **throws away**, reporting nothing to the user at all. So the
honest description of the mobile cold-start is: *the reachable control appears to do nothing
for a minute, and then still appears to do nothing.*

That is the headline, but the pattern underneath it is the finding worth keeping. This
product's machinery is genuinely good — the data spine, the licence stamping, the approve
gate's warning-vs-violation encoding, and the colour system are all careful, well-reasoned
work, and I verified several of their own documented claims and found them accurate to two
decimal places. What is missing is *every surface that tells a human what is happening*.
The clearest single artifact in this audit is one DOM element that carries
`data-plan-state="proposing"` while rendering the words **"No day has been proposed yet."**
The state machine is right. The tests assert the attribute. Nobody rendered the state.

Nine deliverable units were verified through `curl`, `pytest` and `vitest`, and each of those
tools reads attributes and status codes. Every defect in this report lives in the gap between
a correct attribute and a visible pixel.

## 2. Method, and what would invalidate it

**Viewport technique.** Chrome on macOS refuses to size a window below ~400 CSS px, and
`resize_window` did not give reliable exact dimensions (a request for 390 × 1024 produced a
606 × 847 viewport). Measuring the spec's 375 px target was therefore impossible by window
resizing. Instead the app was loaded into a **same-origin iframe sized to exact CSS pixels**,
which gives the embedded document a true 375/390/430 px viewport for layout and media-query
purposes, plus full same-origin JS access for measurement. Every number below is a rendered
`getBoundingClientRect` / `getComputedStyle` value, not an estimate from a screenshot.

**Caveat on that technique, stated plainly:** an iframe reproduces CSS viewport width, media
queries and `vh` units. It does **not** emulate touch input, device pixel ratio, mobile user
agent, or the iOS URL-bar height changes. Findings about *layout, occlusion, size and colour*
are sound. Findings about *touch behaviour specifically* (momentum scroll, tap delay,
`pointer: coarse` media queries) were not tested and are out of scope for these numbers.

**Which code was actually running — this nearly invalidated the audit.** The dev stack on
ports 5173/8000 is **not** served from `main`. Both processes run out of
`/Users/beng/code/siyur/.claude/worktrees/spec-002-plan-compile-offline`, branch
`agent/du06-offline` @ `c0cb945` — another session's checkout (FAIL-011's exact shape: a
shared port reached by a different worktree, invisible to both parties). Before trusting a
single measurement I diffed it:

```
git diff --name-only origin/main c0cb945
docker-compose.yml
scripts/dev.sh
```

**`web/`, `api/`, `planner/` and `commons/` are byte-identical to `origin/main`.** Every
finding therefore transfers to `main` unchanged. Had this diff been non-empty in `web/`, the
whole audit would have needed re-running.

**Recordings.** One GIF was produced — `plan-panel-clipped-390px.gif` (390 px, the plan panel's
inner scroll revealing the two clipped CTAs). It is thin, and that is a limitation to own: the
recorder captures only direct browser-tool actions, and this audit was driven mostly through
JS inside the harness, so most flows exist as screenshots and numbers rather than motion. The
numeric tables in §5 are the durable evidence; the GIF is illustrative only.

**Not tested.** RTL (out of M1 scope by Ben's 2026-08-14 decision — see §7). Real device
hardware. Offline/airplane mode. The `degraded` Overpass path never triggered during the runs.

## 3. Findings

Severity: **blocker** = the journey cannot be completed · **major** = completable but the user
is misled or stranded · **minor** = friction · **polish**.

### Blockers

#### UX-01 — The fast delimit control is unreachable on every phone width · *blocker*

- **Did:** loaded the app at 375, 390 and 430 px and hit-tested every interactive element with
  `document.elementFromPoint` at its own centre, in both scroll states.
- **Expected:** `ux-handoff/README.md` §Screens 1 puts draw/zoom controls on a full-bleed map
  with the bottom sheet below; tap targets ≥ 44 px.
- **Happened:** `Use this view` renders at **y = 66**, and `.siyur-plan-panel` is
  `position: fixed`, `z-index: 3`, starting at **y = 58** — over the controls' `z-index: 2`.
  The button is occluded by `.siyur-plan-panel__title` when the panel is scrolled to top, and by
  `.siyur-plan-form__input` when scrolled to bottom. **There is no scroll position at which it
  is hittable.** Root cause is `plan.css:34-40` — the sole layout media query
  (`width <= 760px`) sets `inset-block: 58px auto; inset-inline: 8px`, anchoring a full-width
  panel at 58 px, which is below the search pill (y 10–44) but above the second controls row.
- **Consequence:** the *only* reachable delimit path is the search pill — see UX-02.
- **Viewport:** 375 ✗, 390 ✗, 430 ✓ (reachable), 1440 ✓.

#### UX-02 — Delimit-by-name: 61.6 s, then a discarded answer · *blocker*

- **Did:** typed a place name, pressed `Find`, watched. Then reproduced against the API directly.
- **Expected:** an area, or a legible reason there isn't one.
- **Happened:** measured end to end —

  | Path | What sends it | Result |
  |---|---|---|
  | `{bbox}` | `Use this view` (occluded, UX-01) | **`200` in 0.18 s** |
  | `{name}` | the search pill (the only reachable one) | **`404` in 61.6 s** |

  The `404` body is not an error — it is a well-designed contract:
  `"20 plausible areas match 'Rhodes Old Town'; ask the user which one"` plus a `candidates`
  array with names, confidences, bboxes and ODbL source stamps. The server refuses to guess,
  correctly.

  **The client discards it.** `web/src/map/areas.ts:85` is
  `if (!response.ok) throw new AreaRequestError(response.status)` — body dropped, status kept —
  and `main.ts:45` routes the throw to `console.warn`. `grep -rn "candidates" web/src/` returns
  **no** match in the area path (the only hits are the plan pipeline's unrelated site count).
  There is no disambiguation UI anywhere in the app.
- **Also:** nothing indicates the request is running. The button stays enabled, no spinner, no
  text change, for the full 61.6 s.
- **Why it's slow, for the fix plan:** `resolve_area.py:119-123` documents it —
  an unwindowed name search is "inherently a full visit of the theme", measured at 73 s
  unwindowed vs **18 s with a caller-supplied window**, `DIVISIONS_TIMEOUT = 120`. The web client
  sends no window, though it has the map viewport in hand.

#### UX-03 — There is no way to sign in · *blocker*

- **Did:** cleared the session cookie and loaded the app cold at 390 px.
- **Happened:** the app renders **identically** to the authenticated state — same map, same
  search pill, same fully-interactive plan form. Nothing indicates you are signed out.
  `GET /auth/login` returns **`503` — "Google SSO is not configured"**, so even a sign-in button
  would dead-end. The only way in is pasting `document.cookie = …` into a devtools console.
- **Meanwhile:** the map's viewport refetch fires on every `moveend`, each returning `401`, each
  logged as `console.warn` and **shown to the user as nothing at all**. I collected **100+**
  identical `SitesRequestError: GET /sites failed with status 401` warnings in a few minutes of
  ordinary panning. The user's experience of being logged out is "the map is empty".

#### UX-04 — The journey dead-ends at approval · *blocker*

- **Did:** traced module reachability from `main.ts` statically, then corrected for dynamic imports.
- **Happened:** **13 modules / 1,976 lines** of built, tested UI are unreachable from the running
  app — `bundle/` (download, index, manifest, open, opfs-protocol, opfs-source, opfs-worker,
  storage, types = 1,290 lines) and `travel/` (index, recovery, render, withheld = 686 lines),
  backed by 829 lines of passing tests. After approving a day the user has nothing to do next
  and no indication anything further exists.
- **Correction to the prevailing description:** these directories are *not* wholly orphaned.
  `plan/parse.ts:28` and `plan/types.ts:11` deep-import `travel/parse` and `travel/types`, and
  `map/basemap.ts:30` imports `bundle/protocol` (reached via a **dynamic** `import()` in
  `main.ts:73`, which a naive static trace misses — my first pass got this wrong). So the data
  contracts are already exercised in production paths; it is the **screens** that are unwired.
  That is good news for sizing the work.

### Major

#### UX-05 — The plan panel clips its own primary CTAs · *major*

`.siyur-plan-panel` is capped at `max-height: 40vh` with `overflow: auto`. Measured content
overflow: **294 px clipped at 390 px**, **365 px at 375 px**, 243 px at 430 px, 0 at 1440 px.
`Plan this day →` and `Approve this day` both sit below the fold of that inner scroller, which
has no visual scroll affordance. They *are* reachable after scrolling inside the panel — I
verified this rather than assuming, and it is why this is major and not a blocker.

#### UX-06 — Validation errors render where they cannot be seen · *major*

Pressing `Plan this day` with no area correctly produces `"Choose an area on the map first."`
and `"Pick the date you are planning for…"` — good validation, on-palette (`#b3542e`). At 390 px
they render at **y = 412 and y = 436**, outside the panel's visible band of **58–428**, and the
panel does **not** scroll them into view. The user taps the button and observes nothing.

#### UX-07 — A live proposal renders as "nothing is happening" · *major*

While `POST /plans` is streaming (`200`, stream open), the review element carries
`data-plan-state="proposing"` and displays:

> No day has been proposed yet. … This day has not been saved yet.

`render.ts:199` **does** contain the right copy — `proposing: 'This day is still being
produced.'` — but it is not reached on this path (`/still being produced/` does not match the
rendered text), and `grep "plan-state" web/src/plan.css` returns **nothing**: the state has no
visual treatment at all. This is the audit's emblematic defect — the attribute a test asserts is
present and correct; the sentence a human reads is the opposite of the truth.

#### UX-08 — Nothing disables during in-flight work · *major*

`.siyur-plan-form` carries `data-pending="false"` and its submit stays enabled throughout a
multi-minute proposal; `Start researching →` stays enabled (`disabled: false`, no
`aria-disabled`) throughout a research pass. Both are re-tappable, queueing duplicate work
against a single-worker API. Contrast `Approve this day`, which *is* correctly
`disabled` + `aria-disabled="true"` — the right pattern already exists in the codebase.

#### UX-09 — The coverage card denies a commons that is there · *major*

For a delimited area the API returned `known_site_count: 958`, `researched_fraction: 0.026`,
`covered: false`. The card rendered:

> Not researched yet · **No cited places here yet**

`web/src/map/areas.ts:191-193` branches only on `coverage.covered` and reads
`known_site_count` **only in the covered branch**; the uncovered branch is a hardcoded string.
So 958 cited places — the product's core asset — are reported to the user as none.

#### UX-10 — The map gets 18% of a map product's screen · *major*

At 390 × 844 the visible map band between the panel (ends y = 428) and the sheet (starts
y = 582) is **154 px — 18.3% of the screen**. In that band: **957 site markers exist in the DOM
and 0 are visible.** A user on a phone sees a map with none of the commons on it.

#### UX-11 — ODbL attribution is covered at every width, including desktop · *major*

`.siyur-sheet` (`z-index: 2`, bottom-anchored) paints over the MapLibre attribution container at
**375, 390, 430 and 1440 px**. At 1440 × 900 the attribution sits at y = 876 (h = 24) and the
sheet at y = 860 (h = 40) — fully covered, opaque background, hit-test confirms `.siyur-sheet`.
`AGENTS.md` calls licensing "mechanical" and requires ODbL attribution on every map; this is the
one finding that is a **compliance** issue rather than a usability one, and it is also the only
defect present on the width the team has always looked at.

#### UX-12 — 11 of 12 controls are below the 44 px floor · *major*

Rendered heights at 390 px (spec floor: **≥ 44 px**):

| Control | Height | |
|---|---|---|
| `siyur-delimit__input` ("Name an area…") | **19 px** | ✗ |
| OSM attribution link | 12 px | ✗ |
| `Find` | 34 px | ✗ |
| `Use this view` | 34 px | ✗ |
| `Plan this day →` | 36 px | ✗ |
| `Approve this day` | 38 px | ✗ |
| plan form inputs (× 5) | 42 px | ✗ |
| interests textarea | 50 px | ✓ |

**Identical at 375, 390, 430 and 1440** — there is no responsive sizing anywhere.

#### UX-13 — Long work has no elapsed time, no cancel, and a frozen label · *major*

A research pass on a real area displayed staged progress (`resolve_area · user · polygon read`
→ `research · overture · 3874 found` → `research · osm · 2357 found`) and then **sat on that
last label for over nine minutes** while the API process held **99% CPU**. There is no elapsed
timer, no percentage, no cancel control, and — per UX-08 — the start button stays enabled. The
user cannot distinguish working from hung. A plan submitted behind it queued for **8+ minutes**
behind the single uvicorn worker, showing UX-07's "No day has been proposed yet" throughout.

*Fairness note:* the single-worker dev server is a dev-stack property, not a shipped
architecture, and I contributed to the contention by starting a plan during a research pass.
The **user-visible** half — no elapsed time, no cancel, no busy signal, re-tappable buttons — is
a product defect regardless of worker count.

#### UX-14 — 1,914 marker DOM nodes on a phone · *major*

957 sites produce **1,914** `.maplibregl-marker` elements (two per site) as absolutely-positioned
DOM overlays. On a 390 px device this is a scroll- and pan-performance hazard, and it grows with
the commons.

### Minor / polish

- **UX-15 — Type is below the floor everywhere.** `ux-handoff/README.md` says mock sizes
  "scale to **≥ 14 px** at real 375–430 px widths". Rendered distribution, identical at all four
  viewports: **9 px × 6, 11 px × 3, 11.5 px, 12 px × 3, 12.5 px, 13 px × 3, 13.5 px**. Exactly one
  element (the delimit input, 14 px) meets the floor. Provenance chips render at **9 px**;
  `RESEARCHING…` at **8.5 px**.
- **UX-16 — Search glyph contrast 4.16 : 1** against a 4.5 floor (`siyur-delimit__glyph`, `⌕`,
  16 px). The only contrast failure found.
- **UX-17 — ADR-0031's reader half is still open, as ADR-0031 itself says.** The compiler emits
  `source.glyphs.sha256` and `source.sprites.sha256` as directory digests
  (`compiler/tiles.py:930-937`) and the schema card specifies both
  (`docs/data/bundle-manifest.md:137-138`), but the client types glyphs as `{ path, license? }`
  with **no `sha256`** and has **no `sprites` field at all** (`web/src/bundle/types.ts:54`), and
  `manifest.ts` drops unknown keys — so **both digests are discarded and never verified.** *This
  is a known, deliberately accepted gap:* the ADR's own header states it in bold and says the
  decision "is not discharged until the launch-time check rejects a mismatched glyph or sprite
  set". The finding is therefore not that it was missed, but that its status reads `accepted` and
  nothing — no test, no lint, no ticket — makes the deferral expire. A hash nothing checks is a
  field, not a guarantee.

## 4. What works — accurately

This matters as much as the defect list, and several of these are better than they need to be.

- **The data spine is solid.** `POST /areas` with a bbox: `200` in **0.18 s** with a resolved
  polygon, licence-stamped source, and a real coverage report. `GET /sites` returned **957**
  records for the viewport. Research streamed genuine staged progress with per-source counts.
- **Provenance and licensing are real.** Every value carries source and licence; the
  `USER · … / OVERTURE · 3874 / OSM · 2357` chips are the design's provenance-stamp motif,
  working. Attribution *renders* correctly — it is only occluded (UX-11).
- **The approve gate is genuinely well designed.** Warnings and violations are separated three
  independent ways: different CSS classes that can never cross-match, **dashed vs solid borders
  (a non-colour separator)**, and distinct hues. I recomputed its documented WCAG figures from
  the hex values and they are accurate: warning text **8.44:1**, violation text **7.69:1**,
  warning border **3.66:1**, section headings 7.56/7.72:1. The CSS comment even discloses that
  the violation border is only **1.88:1** rather than hiding it. That is honest engineering.
- **Contrast is broadly healthy** — measured across all rendered text with resolved effective
  backgrounds: **4.64 : 1 to 15.76 : 1**, one failure (UX-16). Contrast is not this product's problem.
- **The approve button models its own state correctly** — `disabled` + `aria-disabled="true"` +
  a distinct dashed/greyed treatment, and it refuses to enable without a day.
- **Client-side validation is correct and on-palette** — it is only positioned where it cannot be
  read (UX-06).
- **No horizontal overflow at any width.** `scrollWidth === clientWidth` at 375, 390, 430 and
  1440. The classic mobile failure is absent.
- **The CSS is already RTL-ready.** **Zero** physical direction properties
  (`margin-left`, `left:`, `text-align: left`, …) across both stylesheets, against **35** logical
  ones (`inset-inline-start`, `padding-inline`, `border-inline-start`, `inset-block`). This
  materially changes the RTL conversation — see §7.
- **The basemap renders** correctly from PMTiles with local-language labels.

## 7. RTL — deliberately not done

RTL is **out of scope for M1** (Ben, 2026-08-14). The delivery plan and `specs/002/spec.md`
§Assumptions say **M3**; Ben said M2. That discrepancy is flagged to him and is not resolved
here — either way it is not M1. No RTL work was performed and none is proposed.

The cheap-now/expensive-later audit this normally warrants comes back **clean**, which is worth
recording because it is unusual: **zero** physical direction properties across both stylesheets
against **35** logical ones. There is no accumulating RTL debt in the CSS. What is missing is
only the `dir="rtl"` plumbing, the font swaps and the string catalogue — all additive, none of
it made more expensive by F-01…F-13. **Recommendation: keep using logical properties in every
fix above, and RTL stays cheap.** Nothing in this plan needs to change for RTL's sake.
